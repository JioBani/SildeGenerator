# ADR-0002: 연속성 에셋 계획과 전역 이미지 생성 큐

- 상태: 구현 승인
- 작성일: 2026-09-19
- 구현 담당: `pipeline-maintainer`
- 범위: 서버용 프로젝트의 시나리오 분석, 이미지 생성, 관측성, 관리자 화면
- 제외: 모체 프로젝트 수정, 음성/렌더링 전면 재설계, LLM 기반 품질 판정

## 1. 목표

슬라이드 영상의 이미지 생성 시간을 줄이면서도, 여러 장면에 반복되는 인물·장소·사물의 시각적 정체성을 유지한다.

이를 위해 다음 두 축을 함께 도입한다.

1. 시나리오 분석 한 번으로 장면 분할과 연속성 에셋 선정·할당까지 완료한다.
2. 모든 이미지 생성 작업을 전역 공유 큐에 넣고 최대 4개의 슬롯에서 병렬 실행한다.

핵심 원칙은 **연속성 에셋은 기본적으로 0개이며, 필요한 것만 만든다**는 것이다. 에셋을 많이 만드는 것이 품질 자체가 아니며, 불필요한 에셋은 시간과 비용만 늘린다.

### 1.1 사용자 선택형 기능

연속성 유지는 모든 영상에 강제하지 않는다. 작업 생성 화면에 `이미지 연속성 유지` ON/OFF 선택을 제공한다.

- 기본값: OFF. 슬라이드별 다양한 인물과 구도를 허용하고 추가 에셋 생성 시간·비용을 피한다.
- OFF: `continuity_assets=[]`, 모든 장면의 `present_asset_ids=[]`, `reference_asset_ids=[]`; 연속성 기준 이미지 태스크를 만들지 않는다. 공통 Style Bible은 유지하되 동일 인물·장소·사물의 시각적 정체성을 강제하지 않는다.
- ON: 이 문서의 보수적 선정 규칙을 적용한다. ON이어도 연속성 에셋 0개는 정상이며, 모든 장면에 참조를 강제로 채우지 않는다.
- 선택값은 작업 생성 시 고정하며 실행 도중 바꾸지 않는다. 변경하려면 새 작업을 시작한다.
- OFF에서도 직전 장면 이미지를 참조로 쓰지 않는다.

이 선택은 `continuityEnabled` 같은 명시적 boolean으로 API, 작업 레코드, runner 요청, 측정 데이터에 전달한다. 정확한 필드명은 코드 관례에 맞출 수 있으나 암묵적으로 추론하면 안 된다.

## 2. 이 결정이 필요한 사용자 관점의 이유

### 2.1 같은 존재가 다른 존재처럼 보이면 영상 품질이 무너진다

지금은 장면마다 이미지를 독립 생성하므로, 같은 주인공·중요 장소·토템이 다음 장면에서 외형이 달라질 수 있다. 사용자는 이를 단순한 화풍 변화가 아니라 인물이나 장소가 바뀐 것으로 인식한다. 따라서 이야기의 정체성을 결정하는 요소만 기준 이미지를 만들어 장면 생성에 참조로 제공해야 한다.

### 2.2 그러나 모든 명사를 에셋으로 만들면 더 나빠진다

평범한 바나나, 책상, 하늘처럼 모델이 일반적으로 비슷하게 그릴 수 있는 요소까지 에셋으로 만들면 다음 문제가 생긴다.

- 에셋마다 이미지 API 호출이 하나씩 추가된다.
- 첫 장면 생성 전 대기 시간이 길어진다.
- 참조 이미지가 많아져 장면 프롬프트의 자유도와 구도가 제한된다.
- 비용 증가가 실제 시청 품질 향상으로 이어지지 않는다.

따라서 카테고리에 속한다는 사실만으로 선정하지 않는다. **장면 사이에서 모습이 달라졌을 때 시청자가 다른 개체로 오해하거나 서사가 손상되는가**를 기준으로 선정한다. 불확실하면 제외한다.

### 2.3 이미지 생성 대기 시간이 현재 파이프라인의 큰 병목이다

이미지 연산은 외부 서비스가 수행하므로 MINI의 GPU 유무와 직접 관계가 없다. 서로 의존하지 않는 장면을 순차 호출할 이유가 없다. 서로 다른 장면 요청 네 개를 동시에 보내면 로컬 메모리 부담을 크게 늘리지 않으면서 전체 대기 시간을 줄일 수 있다.

### 2.4 앞으로 여러 영상 작업이 동시에 들어온다

동시성 4를 각 영상에 따로 주면 영상 두 개에서 8개, 세 개에서 12개 요청이 나가며 속도 제한과 재시도 폭주가 발생한다. 동시성은 작업별이 아니라 시스템 전체에서 공유해야 한다.

### 2.5 개선 효과를 추측하지 않고 측정해야 한다

프롬프트·모델·참조 수·동시성을 바꾼 뒤 생성시간, 비용, 실패율, 사람의 품질 평가가 어떻게 변했는지 비교할 수 있어야 한다. 그래서 실행 결과뿐 아니라 대기·의존성·제공자 호출·후처리 시간을 분리해 기록한다.

## 3. 시스템 관점의 설계 이유

- 중앙 큐가 동시성, 속도 제한, 재시도 정책을 한곳에서 관리해야 호출 폭주를 막을 수 있다.
- 이미지 소비자가 슬롯 수를 알지 않게 해야 향후 슬롯 수나 공급자를 바꿔도 시나리오/렌더링 코드를 수정하지 않는다.
- 의존성 그래프를 사용하면 참조가 없는 장면은 즉시 시작하고, 참조가 필요한 장면만 해당 에셋을 기다릴 수 있다.
- 직전 장면 이미지를 다음 장면의 참조로 쓰면 오류가 연쇄적으로 누적되고 모든 장면이 순차 의존하게 된다. 기준 에셋만 참조해야 실패와 재시작을 장면 단위로 격리할 수 있다.
- 구조화된 시나리오 분석 결과를 결정론적으로 검증·조합하면 별도의 LLM 호출을 늘리지 않고도 프롬프트를 생성할 수 있다.
- Redis는 큐·lease와 같은 일시적 조정에, PostgreSQL은 작업·시도·측정값과 같은 영속 기록에 적합하다. 이미지와 전체 프롬프트 같은 큰 산출물은 작업 파일시스템에 두고 DB에는 경로·해시·색인만 둔다.

## 4. 확정한 연속성 에셋 카테고리

카테고리는 선정 후보를 분류하기 위한 것이며, 카테고리에 포함된다고 자동 선정되는 것은 아니다.

| 값 | 의미 | 예시 |
|---|---|---|
| `character` | 사람, 동물, 생물, 의인화 로봇 | 주인공, 반복 등장하는 안내 로봇 |
| `object` | 소품, 토템, 유물, 무기, 제품, 장치 | 고유 문양이 있는 열쇠, 핵심 장치 |
| `location` | 실내, 건물, 도시, 자연환경, 세계, 행성 | 반복되는 연구실, 고유한 미래 도시 |
| `vehicle` | 육상·철도·항공·해상·우주 이동수단 | 주인공의 우주선 |
| `graphic` | 로고, 상징, 지도, 문서, 카드, 표지판, 인터페이스 | 조직 로고, 핵심 지도 |
| `phenomenon` | 포털, 고유 에너지, 마법, 이상현상, 특징적 기상 | 반복되는 청색 균열 |

다음은 에셋 카테고리가 아니다.

- 화풍·색감: Style Bible로 관리한다.
- 시간대·날씨·의상·손상 상태: 에셋의 장면별 상태로 관리한다.
- 차량 내부가 반복되는 독립 공간이라면 `location` 후보가 될 수 있지만, 선정 기준을 별도로 통과해야 한다.

## 5. 선정 기준

### 5.1 기본값

- `continuity_assets: []`는 정상이며 오히려 선호되는 결과다.
- 최소 에셋 수와 최소 참조 이미지 수를 두지 않는다.
- 반복 등장한다는 이유만으로 선정하지 않는다.
- 불확실하면 제외한다.

### 5.2 사용자 고정 항목이 아닌 자동 후보의 선정 조건

다음을 모두 만족하는 경우에만 선정한다.

1. 같은 식별 가능한 개체가 생성될 이미지 기준 두 장면 이상에 나타난다.
2. 화면에서 알아볼 수 있는 크기와 중요도로 나타난다.
3. 외형 불일치가 시청자에게 다른 존재로 느껴지거나 서사를 손상한다.
4. 텍스트 설명만 반복하는 것보다 기준 이미지가 일관성을 의미 있게 개선한다.
5. 추가 생성 시간과 비용을 감수할 가치가 있다.

예: 일반적인 바나나는 제외한다. 그러나 여러 장면에서 단서로 쓰이는 빨간 봉인이 찍힌 특정 바나나는 `object`로 선정할 수 있다.

### 5.3 상태 변화

의상 변경, 파손, 시간대 변화 등은 새 에셋을 만들지 않고 동일 에셋의 `states`로 표현한다. 정체성이 실제로 바뀌는 별도 개체일 때만 새로운 에셋이다.

### 5.4 자기 가지치기

분석 프롬프트는 후보를 만든 뒤 다음 질문으로 한 번 더 제거해야 한다.

> 이 항목의 기준 이미지를 만들지 않아도 대부분의 장면에서 시청자가 같은 존재로 받아들이는가?

그렇다면 제외한다. 디버깅용으로 경계 후보를 남길 경우에도 최대 10개와 짧은 사유 코드만 기록하며, 모든 명사를 열거하지 않는다.

## 6. 시나리오 분석은 한 번의 Codex 호출에서 끝낸다

장면 분할과 연속성 분석을 별도 LLM 호출로 나누지 않는다. 동일한 Codex 시나리오 분석 요청에 다음 프롬프트 문서를 합성한다.

- `director/system.md`
- `storyboard/split-scenes.md`
- `continuity/select-assets.md`
- `continuity/assign-scene-references.md`

기능별 문서는 분리해 관리·버전 관리하지만 런타임 호출은 한 번이다. 이 호출에서 아래를 모두 산출한다.

1. 원문 보존 장면 분할
2. 연속성 에셋 선정
3. 에셋의 정체성·불변 요소·허용 변화 정의
4. 각 장면에 실제 등장하는 에셋 할당
5. 각 장면 생성에 실제 참조로 넣을 에셋 선택

`present_asset_ids`와 `reference_asset_ids`를 반드시 분리한다. 어떤 장소가 장면에 나오더라도 배경에 작게 보이고 중요하지 않다면 `present_asset_ids`에는 있으나 `reference_asset_ids`에는 없을 수 있다.

별도의 LLM이 참조 이미지를 고르게 하지 않는다. 프로그램은 JSON 스키마, ID, 상한, 의존성, 파일 경로만 결정론적으로 검증·해석한다.

연속성 OFF인 작업은 에셋 선정용 긴 지시문을 Codex 요청에 포함하지 않는다. 동일한 안정적 출력 schema를 유지하기 위해 빈 연속성 배열을 요구하는 짧은 비활성화 지시만 합성한다. 관리자 프롬프트 snapshot에는 실제 요청에 사용된 문서와 비활성 문서를 구분해 기록한다.

## 7. 분석 출력 계약

기존 scene-plan strict JSON schema에 다음 개념을 추가한다. 실제 언어별 타입 이름은 코드베이스 관례에 맞추되 의미를 바꾸지 않는다.

```json
{
  "continuity_assets": [
    {
      "asset_id": "asset-character-001",
      "category": "character",
      "name": "주인공 민서",
      "canonical_identity": "외형과 정체성을 식별할 수 있는 구체적 설명",
      "must_remain_consistent": ["얼굴 윤곽", "짧은 검은 머리", "주황색 브로치"],
      "allowed_variations": ["표정", "포즈", "조명"],
      "states": [{"state_id": "default", "description": "기본 상태"}],
      "appearing_scene_ids": ["scene-001", "scene-004"],
      "selection_reason_code": "IDENTITY_CRITICAL",
      "selection_reason": "외형이 바뀌면 다른 주인공으로 보임",
      "failure_if_inconsistent": "장면 간 주인공 정체성 단절",
      "confidence": 0.94,
      "anchor_prompt": "결정론적 기준 이미지 템플릿에 삽입할 설명"
    }
  ],
  "scenes": [
    {
      "scene_id": "scene-001",
      "present_asset_ids": ["asset-character-001"],
      "reference_asset_ids": ["asset-character-001"]
    }
  ],
  "rejected_borderline_candidates": [
    {"name": "바나나", "reason_code": "GENERIC_APPEARANCE"}
  ]
}
```

결정론적 검증 항목:

- 카테고리는 위 6개 enum만 허용한다.
- ID는 작업 안에서 고유하고 안정적이어야 한다.
- 장면의 에셋 ID는 선정된 에셋만 가리킨다.
- `reference_asset_ids`는 기본 0~8개, 공급자 하드 상한은 16개다.
- 8개 초과는 명시적 내부 override가 있을 때만 허용하며 16개를 넘으면 항상 거부한다.
- 같은 ID의 중복 참조와 존재하지 않는 상태 참조를 거부한다.
- 원문 나레이션의 누락·재작성 여부는 기존 원문 보존 검증을 유지한다.
- reconcile 단계가 유효한 에셋 할당을 조용히 삭제해서는 안 된다. 보정했으면 이벤트와 이유를 남긴다.

## 8. 에셋당 기준 이미지는 정확히 한 장 생성한다

선정된 연속성 에셋마다 기준 이미지 한 장만 만든다. 자동 다각도·표정 시트·복수 변형은 만들지 않는다.

카테고리별 기본 구도:

- `character`: 단순 배경, 얼굴이 보이는 3/4 전신 또는 정체성이 가장 잘 드러나는 구도
- `object`: 형태·재질·크기를 알 수 있는 3/4 구도
- `location`: 구조와 고유 특징이 보이는 대표 와이드샷
- `vehicle`: 외형을 식별하기 좋은 3/4 외관
- `graphic`: 왜곡 없는 정면, 평면 표현
- `phenomenon`: 고유 형태와 색이 드러나는 대표 활성 상태

장면별 포즈·시점·조명·손상·의상 등은 장면 프롬프트에서 지시한다. 기준 이미지를 추가 생성하지 않는다.

동일 작업 안에서는 에셋당 정확히 하나의 생성 태스크만 존재해야 한다. 안전하게 재사용할 수 있는 경우 `에셋 정의 + Style Bible + 프롬프트 문서 버전 + 모델 설정` 해시로 캐시할 수 있다. 캐시 적중·미적중도 기록한다.

## 9. 직전 장면 연결은 제거한다

현재 런타임의 `needs_reference_image(scene)`와 `previous_image_path` 기반 연쇄 참조를 제거한다. 장면 이미지의 입력 참조는 선정된 연속성 에셋 기준 이미지뿐이다.

이유:

- 직전 장면의 오류가 다음 장면으로 전파된다.
- 앞 장면이 끝나야 다음 장면을 만들 수 있어 병렬화가 불가능하다.
- 재시도·재개 시 장면 간 숨은 의존성이 생긴다.
- 직전 장면 구도와 배경을 불필요하게 복사할 수 있다.

코드 어디에도 직전 생성 장면을 암묵적 fallback reference로 쓰는 경로를 남기지 않는다.

## 10. 전역 이미지 생성 브로커와 4개 슬롯

### 10.1 소비자 계약

연속성 에셋, 장면, 수동 재생성, 향후 복구 기능 등 모든 이미지 소비자는 동일한 `ImageTaskBroker` 추상화를 사용한다.

소비자는 다음만 수행한다.

1. 이미지 작업과 의존성을 등록한다.
2. 결과 artifact를 기다리거나 상태를 구독한다.

소비자는 슬롯 수, 현재 동시성, 재시도, 공급자 속도 제한을 알거나 직접 구현하면 안 된다. 이미지 worker 외부에서 공급자를 직접 호출하는 코드 경로를 두지 않는다.

### 10.2 동시성 의미

- 초기 전역 동시성: 4
- 이는 한 영상당 4가 아니라 시스템 전체 in-flight 4다.
- 서로 다른 프롬프트의 요청 네 개를 각각 `n=1`로 보낸다.
- 서로 다른 네 장면을 한 요청의 `n=4`로 만들지 않는다.
- 고정 4개 배치가 아니라 work-conserving pool이다. 한 슬롯이 끝나면 준비된 다음 작업을 즉시 받는다.

### 10.3 의존성

- 참조가 없는 장면은 분석 직후 바로 `ready`가 된다.
- 참조 에셋이 있는 장면은 필요한 기준 이미지 태스크가 모두 성공한 뒤 `ready`가 된다.
- 기준 에셋이 실패하면 그것을 참조하는 장면만 명시적으로 차단한다.
- 슬롯은 순서를 모르며 `ready` 작업만 가져간다.

### 10.4 상태와 데이터

이미지 태스크 상태:

`waiting_dependencies`, `queued`, `leased`, `running`, `retry_wait`, `succeeded`, `failed`, `cancelled`

필수 필드:

- `image_task_id`, `job_id`, `task_type`
- `scene_id` 또는 `asset_id`
- provider/model/quality/size/input_fidelity
- prompt bundle version, 문서별 version/SHA, compiled prompt path/SHA
- reference asset IDs, reference file paths/hashes, 순서
- dependency task IDs
- output path/hash
- attempt, lease owner, 상태별 timestamp

PostgreSQL에는 태스크·시도·측정값을 영속 저장한다. Redis에는 대기열, lease, 전역 semaphore 같은 일시적 조정 상태를 둔다. 이미지·전체 합성 프롬프트·응답 transcript는 작업 파일시스템에 저장하고 DB에는 경로와 SHA-256만 저장한다.

현재 Nest의 영상 작업 BullMQ와 이미지 큐는 별도 관심사다. 구현은 기존 구조와 장애 복구 특성을 보고 Redis Streams, BullMQ 연동 또는 durable DB + Redis queue 중 최소 결합 방식을 선택할 수 있으나, Python runner가 Nest 내부 구현에 취약하게 결합되면 안 된다. 외부 계약은 `ImageTaskBroker`로 고정한다.

### 10.5 여러 영상 사이의 공정성

앞으로 제한된 병렬 영상 생성이 예정되어 있다. 긴 영상 하나가 네 슬롯을 계속 독점하지 않도록 job 간 round-robin 또는 동등한 fair-share를 적용한다. 의존 장면을 많이 해제하는 기준 에셋 작업에는 제한된 우선순위를 줄 수 있지만 다른 job을 starvation시키면 안 된다.

취소 시 queued 작업은 즉시 취소하고, 이미 외부 호출 중인 태스크는 안전하게 결과를 폐기하거나 완료 후 cancelled로 정리한다.

## 11. 이미지 공급자와 GPT Image 2.5

목표 모델은 `gpt-image-2.5-sunburst`다. 현재 시스템은 사용자의 분석 우선 지시에 따라 아직 `gpt-image-2`에 남아 있으므로 이 ADR 구현 담당자가 통제된 테스트 후 전환한다.

공식 API 기준 편집 요청은 참조 이미지 최대 16개를 받을 수 있다. 다만 현재 ChatGPT OAuth 브리지는 `/v1/models`에 `gpt-image-2`만 광고하면서도 명시적인 2.5 저해상도 테스트는 성공한 전력이 있다. 따라서 모델 목록만 신뢰하지 말고 실제 compatibility smoke test를 둔다.

배포 전 OAuth 경로에서 아래를 실제 확인한다.

- 2.5 단일 이미지 생성
- 참조 이미지 2개와 4개의 multipart 전달
- 참조 순서와 결과 매핑
- `input_fidelity=high` 지원 여부
- 응답 usage 구조

provider는 현재 단일 `reference_path`가 아니라 순서가 보존된 복수 참조를 받도록 바꾼다. 합성 프롬프트에는 각 참조를 다음처럼 명시적으로 매핑한다.

- 참조 번호와 `asset_id`
- 반드시 유지할 정체성 특징
- 장면에서 허용되는 변화
- 복사하면 안 되는 배경·포즈·프레이밍

기본 제안은 기준 에셋 `sunburst/high`, 장면 `sunburst/medium`이지만, 관리자 설정과 실제 측정 결과로 확정한다. 처음에는 변수 격리를 위해 동일 품질로 시작해도 된다.

현재 1536×1024를 1920×1080으로 자르면서 구도 손실이 생길 수 있다. 2.5가 16의 배수 크기를 지원하는지 OAuth 실호출로 검증한 뒤 `1920×1088` 생성 후 8px trim 같은 근접 16:9 방식을 검토한다. 확인 없이 운영 기본값으로 넣지 않는다.

## 12. 프롬프트 파일 구성

다음 문서를 기능별로 추가하고 기존 관리자 프롬프트 관리·버전 묶음에 포함한다.

- `continuity/select-assets.md`: 보수적 에셋 선정, 0개 허용, 반례와 자기 가지치기
- `continuity/assign-scene-references.md`: 등장과 실제 참조 분리, 장면당 0~8개
- `continuity/build-canonical-asset.md`: 카테고리별 기준 이미지 직접 생성 템플릿
- `image/reference-contract.md`: 참조 번호와 보존/변경/비복사 규칙
- `image/generate-scene.md`: 장면 이미지 합성 템플릿

앞의 두 문서는 시나리오 분석의 같은 Codex 요청에 합성한다. 뒤의 세 문서는 구조화된 분석 결과와 Style Bible을 결정론적으로 보간하여 이미지 프롬프트를 만든다. 이미지 프롬프트 작성만을 위한 추가 LLM 호출은 하지 않는다.

관리자 화면에는 각 문서의 사용 시점, 사용 조건, 입력 변수, 사용 주체, 현재/예약 상태를 정확히 표시한다. 문서 수정은 새 버전을 만들고 작업 시작 시 prompt bundle snapshot을 고정한다. 실행 중 수정이 이미 시작한 작업에 섞이면 안 된다.

## 13. 재시도와 복구 정책

- 최초 호출 + 최대 2회 재시도, 총 3회
- 네트워크 오류, 명시적 429, 재시도 가능한 5xx만 자동 재시도
- schema/validation 오류, 일반 4xx, 정책 거부, 사용자 입력 수정이 필요한 오류는 같은 입력으로 재시도하지 않음
- exponential backoff + jitter
- 연속 429가 발생하면 중앙 scheduler가 유효 동시성을 4→2→1로 줄이고 건강한 구간 뒤 점진 복구
- 실패한 태스크만 다시 실행하고 성공한 이미지와 에셋은 재생성하지 않음
- timeout은 공급자가 이미 사용량을 소비했을 수 있으므로 시도별 잠재 중복 비용을 기록
- 시도별 임시 디렉터리에 원자적으로 저장한 뒤 성공 파일만 최종 경로로 promote
- 재개 시 성공 상태, 출력 hash, 파일 존재와 무결성을 확인해 재사용

## 14. 측정과 관리자 노출

### 14.1 시도별 원시 측정

각 이미지 호출 시도에 다음을 기록한다.

- 식별자: image task/job/scene/asset/type, provider request ID
- 설정: provider, model, quality, size, input fidelity, 프롬프트 묶음 버전과 SHA
- 참조: 개수, 순서, asset IDs, 파일 hash/bytes
- 시간: submitted, dependency-ready, queued, leased, provider-start, response-received, decode/postprocess, persisted
- 파생 시간: dependency wait, queue wait, provider duration, postprocess, total
- scheduler: slot/worker ID, 시작 당시 active 수, 설정/유효 동시성, queue depth, job share, retry/backoff
- usage: text input, image input, cached input, output image, total token 또는 공급자가 주는 동등 usage
- 비용: 참조 입력, 출력, 해당 시도 실제/환산 USD·KRW, 재시도 낭비 비용
- 결과: HTTP status, 안정적인 error code, revised prompt, 출력 경로/hash/bytes/dimensions

공급자 raw usage는 보존하되 API 키·인증 헤더·민감정보는 절대 기록하거나 노출하지 않는다. 가격표 버전과 적용 환율 snapshot을 함께 저장해 과거 비용이 나중에 바뀌지 않게 한다.

### 14.2 결정론적 이미지 검사

LLM을 사용하지 않고 다음 기술 검사만 수행한다.

- 디코딩 가능 여부
- 크기와 종횡비
- 파일 크기
- 빈 이미지/과도한 단색
- 픽셀 분산·entropy
- 평균 밝기와 highlight/shadow clipping
- blur/sharpness(Laplacian 등)
- pHash 중복, 필요 시 SSIM

이는 미학이나 의미 일치 점수가 아니라 기술적 신호다. 의미·예술 품질은 기존처럼 사람이 평가하고 이미지/영상 품질 점수와 메모를 저장할 수 있게 한다.

### 14.3 관리자 화면

다음을 조회·비교할 수 있게 한다.

- 전역 queue depth, 설정/유효 동시성, 슬롯 사용률과 idle 시간
- 슬롯별 Gantt/timeline
- images/min, dependency/queue/provider 시간 p50/p95
- 재시도율, 실패율, 429 비율
- 영상별 연속성 에셋 수와 에셋 생성이 critical path에 더한 시간
- 참조 없는 장면 비율과 참조 개수 분포
- 에셋/장면/재시도/수동 재생성별 시간과 비용 분해
- 영상 1개당 합계와 완성 영상 1분당 합계
- 프롬프트 버전, 모델, quality, 참조 개수, 동시성별 생성시간·비용·품질 비교
- 연속성 ON/OFF별 생성시간·비용·품질, 평균 에셋 수, 평균 참조 수 비교

기존 개선 분석 화면과 프롬프트 버전 비교 구조를 확장하며 mock 데이터와 Live 데이터를 섞지 않는다.

## 16. 필수 테스트

### 16.1 분석/프롬프트 단위 테스트

- 연속성 요소가 없는 대본은 빈 배열
- 일반 바나나는 제외
- 반복되는 고유 봉인 바나나는 선정
- 동일 인물의 상태 변화가 별도 에셋으로 중복되지 않음
- 잘못된 category/ID/state/reference cap 거부
- 원문 나레이션 완전 보존
- reconcile 후 에셋 할당 유실 없음

### 16.2 큐 결정론적 테스트

- 여러 job을 합쳐도 active provider call은 항상 4 이하
- 고정 batch barrier 없이 빈 슬롯이 다음 ready task를 즉시 실행
- 참조 의존 장면은 에셋 완료까지 대기
- 무참조 장면은 즉시 실행
- job 간 공정성, cancellation, resume
- 성공 artifact의 exactly-once final promotion
- 오류 종류별 retry/no-retry와 adaptive concurrency

### 16.3 provider 계약 테스트

- 참조 0, 1, 2, 4, 8개
- 참조 순서와 asset mapping 보존
- 일반 장면 8개 초과는 override 없으면 거부
- 16개 초과는 항상 거부
- response usage와 오류 정규화

### 16.4 측정 정합성 테스트

- 모든 태스크의 모든 시도가 집계에 포함
- 시도별 usage/cost 합계가 job 합계와 일치
- 재시도 낭비 비용 분리
- 시간 구간 합계 오차가 정의한 허용 범위 안
- mock과 Live 비교군 분리

6. mock 429/5xx로 감소·재시도 검증
7. 약 10초 한국어 영상 완주 및 시각 검수
8. 같은 프롬프트/모델/설정으로 기존 순차 대비 wall time 비교

실 Live 호출에서 불필요한 재시도와 비용을 발생시키지 않는다. 비밀키는 화면, 로그, 테스트 artifact에 남기지 않는다.

## 17. 완료 기준

- 작업당 Codex 시나리오 분석 호출은 장면+연속성 계획을 포함해 한 번이다.
- 생성 화면에서 이미지 연속성 유지 ON/OFF를 선택할 수 있고 기본값은 OFF다.
- OFF 작업은 연속성 프롬프트 분석·에셋 생성·참조 이미지 입력을 실행하지 않으며, ON 작업만 보수적 연속성 파이프라인을 실행한다.
- 작업 상세와 개선 분석에서 실제 적용된 연속성 모드를 확인·비교할 수 있다.
- 6개 카테고리와 보수적 선정 기준이 적용되고 빈 에셋 목록이 정상 처리된다.
- 선정 에셋마다 기준 이미지는 정확히 한 장이다.
- 장면 참조는 기본 0~8, 하드 상한 16이다.
- 직전 장면 출력 이미지를 참조하는 코드 경로가 없다.
- 모든 이미지 생산자가 공유 broker를 사용하고 worker 밖에서 provider를 직접 호출하지 않는다.
- 여러 영상이 동시에 있어도 전역 in-flight는 4를 넘지 않는다.
- 독립 작업은 슬롯이 비는 즉시 실행된다.
- 실패/재시도 시 성공한 이미지가 재생성되지 않는다.
- 태스크·시도별 시간, usage, 비용, 참조, 프롬프트 버전이 추적된다.
- 관리자에서 queue/slot과 프롬프트·모델·설정별 개선 지표를 비교할 수 있다.
- 단위·통합·mock E2E와 MINI Live E2E가 모두 통과한다.
- 모체 프로젝트와 관련 없는 사용자 변경은 수정하지 않는다.

## 18. 명시적 비목표

- 직전 장면 이미지 연쇄 참조
- 에셋당 자동 복수 기준 이미지
- 최소 에셋 수 또는 최소 참조 수 강제
- 모든 명사를 에셋화
- 의미/미학 검사용 추가 LLM 루프
- 서로 다른 장면을 한 요청의 `n=4`로 생성
- 고정 4개 batch가 모두 끝날 때까지 기다리는 방식
- 무제한 또는 job별 4개 동시성
- 이미지·전체 프롬프트·transcript 바이너리/본문을 DB에 직접 저장
- 이 기능과 무관한 음성·렌더링·사용자 연출 옵션 전면 변경

## 19. 구현 담당자의 재량과 보고

Redis/BullMQ/Python runner 사이의 구체적 IPC 방식은 기존 장애 복구·배포 구조를 확인한 뒤 가장 단순하고 내구성 있는 방식을 선택할 수 있다. 다만 외부 소비자 계약, 전역 동시성, 영속성, 관측성, 완료 기준은 유지한다.

구현 중 API 제약 때문에 본 결정을 바꿔야 하면 조용히 우회하지 말고 다음을 사용자에게 먼저 제시한다.

1. 확인된 제약과 재현 증거
2. 사용자 품질·시간·비용에 미치는 영향
3. 가능한 대안과 권장안
4. 비교 측정을 어떻게 보존할지
